# NVIDIA

The `nvidia` and `nvidia-lts` applications supply the curated NVIDIA open driver for supported Turing and newer cards. Install it with `incus admin os application add nvidia`, then reboot if the API requests it. Installation also adds `gpu-support` for Nouveau fallback firmware. AMD, Intel and older NVIDIA cards continue to use their in-kernel drivers and the `gpu-support` firmware application.

The application contains modules built for this OS kernel and signed once with the image key, matching GSP and ucode firmware, CUDA and NVML libraries, `nvidia-smi`, `libnvidia-container`, and the NVIDIA Container Toolkit. Incus supplies its LXC NVIDIA hook; this application supplies the `nvidia-container-cli` that hook invokes for `nvidia.runtime=true`. Real GPU and container workload validation is required before production use.

## Curated branches

The curated default, `nvidia`, uses NVIDIA’s **newest long-term branch**, currently **620.70.06 (R620)**. `nvidia-lts` supplies **580.196.07 (R580)** for older CUDA software and as the rollback branch. NVIDIA's [driver support matrix](https://docs.nvidia.com/datacenter/tesla/drivers/latest/supported-drivers-and-cuda-toolkit-versions.html), updated November 4, 2026, designates both R620 and R580 as **Long Term Support Branches**; R595 is the separate Production Branch. These application names distinguish the newest curated LTS from the previous LTS. Arca picks the newest LTS over the Production Branch (R595) for its longer support window and fewer forced driver moves. The matrix lists R620 support through September 2029, compared with March 2027 for R595.

Both packs use the open kernel modules and support Turing and later. NVIDIA's [R580.196.07 compatibility table](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/580.196.07/README.md#compatible-gpus) explicitly includes the Ada GeForce RTX 4060 Ti (`2805`). Neither pack enables the proprietary kernel modules or support for pre-Turing cards.

Install the other branch using the normal application API, for example `POST /1.0/applications` with `{"name":"nvidia-lts"}`. This replaces the requested branch in the same state slot and retains the previous pack. There is only one linked NVIDIA extension. Installing the other branch explicitly is allowed while pinned; the pin continues to prevent automatic updates within the requested branch. Version changes use `POST /1.0/applications/<branch>/:switch-version` with `{"version":"<cached build>"}`. An empty version selects `state.previous`, including a previous build from the other branch, entirely from disk.

## Driver choice

The application configuration has `driver: nvidia` (the installed default) or `driver: off`. `off` disables the NVIDIA application driver and uses Nouveau. The `cards` map overrides individual PCI addresses with `nvidia`, `vfio-pci`, or `off`; a card set to `off` stays unbound. For example:

```yaml
config:
  driver: nvidia
  pin_current_versions: false
  cards:
    "0000:01:00.0": nvidia
    "0000:02:00.0": vfio-pci
```

PCI addresses are stored in lowercase. Per-card choice changes and removal require a reboot. Explicit application API branch and cached-version switches may run live when no process holds `/dev/nvidia*` and NVIDIA modules have no external users or foreign module holders: verify the replacement, remove only the NVIDIA link and refresh, unload the previous modules, link and refresh the replacement, load its modules and check every assigned GPU with `nvidia-smi`. References from NVIDIA’s own dependent modules are discounted, so an idle loaded driver can switch live. If a new user appears after detach, the active pack is relinked before deferring. Incus and every other extension remain merged throughout. Unattended update checks stage the new build for the next boot and set `needs_reboot`; they never switch drivers live. If device-use inspection fails, a process holds a device, or modules cannot unload, the switch waits for the next boot. The API reports `state.needs_reboot` and a plain `state.reason`; the system update state also reports the required reboot. Existing system PCI passthrough configuration takes precedence, including vendor/device assignments. Address-specific passthrough uses `driver_override` instead of registering a device ID, so an identical second card remains independently assignable.

The base image suppresses Nouveau and NVIDIA autoload. The boot preparation service generates modprobe configuration, sets per-address overrides, and explicitly loads drivers after the extensions merge. Nouveau remains available for unsupported cards and fallback. The NVIDIA DRM module is loaded with `modeset=1 fbdev=1` to preserve a GPU console. `gpu-support` does not unbind or reload either NVIDIA driver.

## Health and recovery

After boot, `nvidia-smi` must initialise every PCI address assigned to NVIDIA. A failed bind or health check records the reason. Boot failures without a previous pack quarantine that driver version for this OS release in `state.bad_versions`; switches record a release/branch/build quarantine in `state.bad_builds`. When a previous pack exists, recovery verifies it again and restores it from disk without downloading anything. The failed requested branch/build and the pin remain visible; the reason states that the previous driver was restored. If live recovery cannot complete, runtime recovery unloads failed modules when possible, saves the previous pack as requested for the next boot, and reports `the new NVIDIA driver failed its check; restart to go back to the previous driver`. Runtime driver changes never reboot the host automatically. A marker in `/run` permits the startup health check only once per boot, so restarting the daemon while Incus is running cannot repeat the boot probe or reboot. Only that boot-time startup, before Incus starts, may request at most one automatic recovery reboot after durably saving the failure and boot marker. Failure quarantine prevents automatic retries. Before module loading, a durable attempt marker records the OS release, driver version and boot ID. A binding attempt left by an interrupted boot blocks that version at the next boot. Successful binding clears that marker immediately. A separate health marker is saved just before `nvidia-smi` runs; an interrupted health probe quarantines the driver, while an interruption between binding and health checking does not by itself do so. Preparation has a 120-second deadline. A failed boot-time health check requests at most one automatic fallback reboot per boot, after the quarantine state has been saved and synced to disk; refused or failed saves never trigger an automatic reboot. An installation with no GPU reports `no NVIDIA GPU` and stays on Nouveau without blocking the driver version. Assigning every card to VFIO or off, or blacklisting NVIDIA, also leaves the version eligible. `state.reason` is available to management clients. A quarantined driver is not retried automatically on the same OS release. Reinstalling or updating the application clears its applicable failure entry after the signed replacement has been verified and before extension selection. A quarantined link reports `this NVIDIA driver version failed its check; it stays off until it's updated or reset`. Only bind or health failures quarantine a build; cancellation and transient errors defer without quarantine. Verification errors leave the working driver untouched. Set `config.reset_bad_versions: true` to clear failure history explicitly; this is a one-shot field and returns to false after saving.

The app checks its installed version metadata against `modinfo -F version` and requires every firmware file reported by the built module. Both boot-time and daemon-triggered extension refreshes verify the signed image and compare its declared kernel to the running kernel before merging it. A mismatched or unverifiable NVIDIA image is excluded without blocking Incus or other applications. The recorded reason is `the NVIDIA driver for this Arca OS version is not installed yet`. A new driver pack downloaded before its OS is retained on disk while the old matching pack stays linked. Before the first extension merge after a kernel change, the boot guard selects the newest verified matching on-disk build, respecting the pin, so preparation can load it on that same boot. If none matches, Nouveau is used and startup and update checks continue. If a matching build becomes available only after preparation, the API sets `needs_reboot` with the reason `reboot to enable NVIDIA`. After a successful selection, the active build, requested build, previous rollback build and build for the other boot slot are retained; other NVIDIA images are pruned. A refresh that selects no image never prunes NVIDIA packs. If the other boot slot cannot be identified, pruning waits until its release is known. `state.requested_branch` and `state.version` record the requested branch and downloaded build; `state.active_branch` identifies the merged branch; `state.previous` identifies the retained rollback branch/build; `state.active_extension_version` reports the compatible image actually merged. Keeping these separate avoids repeatedly downloading a pending build or clearing the old driver's quarantine. `pin_current_versions` prevents automatic downloads and pins the requested build. An already-active matching build may remain while its replacement awaits the OS update. If neither matches after a kernel bump, Nouveau is used until the pin is removed or a compatible build is explicitly installed.

Before any `insmod`, every shipped module's detached CMS signature is verified against the OS certificates in `/usr/lib/verity.d`, including during sysinit before ZFS raises kernel lockdown. The signed dm-verity extension also protects the module bytes against changes between verification and loading.

Modules are loaded by full path in dependency order, with base-kernel dependencies loaded by modprobe. This avoids replacing the base image's `modules.dep` with an extension-specific index. NVIDIA variant names are selected at application load and share one implementation and state slot; both curated branches use the same build, signing, verification, health and recovery implementation.

## Sources and licences

`mkosi.images/nvidia/version` and `mkosi.images/nvidia-lts/version` are the driver version sources for their respective branches. Each branch has its own `artifacts.json`; the LTS branch invokes the same build and installer scripts. NVIDIA's official redistributable archives contain the complete open module source, firmware and userspace for that version. SHA256 pins in `artifacts.json` cover those archives and the official NVIDIA repository packages for the toolkit; no generated GitHub tag archive or executable installer is used. The R580 archive pins come from NVIDIA’s [580.196.07 redistributable manifest](https://developer.download.nvidia.com/compute/nvidia-driver/redist/redistrib_580.196.07.json). The modules are built directly without DKMS or a temporary signing key.

The open modules are distributed under their permissive MIT or BSD licence option; the NVIDIA userspace and firmware have NVIDIA's redistribution licence. The Container Toolkit and the pinned `libnvidia-container` packages are Apache-2.0; bundled BSD and MIT components have their own notices. The application ships the NVIDIA licence and open module COPYING under `/usr/share/licenses/nvidia`, and the container packages' copyright and licence notices under `/usr/share/doc/`. Review those files when redistributing an image.
